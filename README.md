# Origina Protocol

Origina Protocol is open-source infrastructure that permanently anchors a cryptographic fingerprint of AI-generated media at the moment of creation, so any platform can verify a file's origin and authenticity — without ever storing, uploading, or transmitting the media file itself.

This repo has two parts:

- **`anchor/`** — the Solana program (Anchor/Rust): a registry of approved providers and one provenance record per file. Maintained by the program's author; not edited from the app side.
- **`app/`** — the Origina web app (Next.js). It computes fingerprints in the browser and talks to the program through a typed client generated from the program's IDL.

## How it works

1. A **registry authority** approves *providers* (AI tools / platforms) and each provider **claims** its registration by signing with its own wallet.
2. An approved provider **anchors** a file: the app fingerprints the image in the browser (SHA-256 for exact matching, a 64-bit perceptual hash for near matching) and the provider's wallet signs an `anchor_media` transaction. One immutable record account is created per `(provider, file)`.
3. Anyone can **verify** an image: the app fingerprints it and looks it up on-chain — exact SHA-256 match first, then the closest perceptual hash within Hamming distance 12. No wallet is needed to verify.

The image never leaves the browser; only its fingerprint goes on-chain.

### What the app writes (and the choices it makes where the program leaves room)

The program's record is: `provider`, `file_sha256`, optional `perceptual` (algorithm + 32-byte hash), `c2pa_manifest_hash`, optional `creator_wallet`, `slot`, optional `generated_at` — 189 bytes, about 0.0022 SOL of one-time rent.

- **`c2pa_manifest_hash`** must be non-zero, but the app doesn't read C2PA manifests yet. Records carry a fixed sentinel: SHA-256 of `origina:no-c2pa-manifest:v1`.
- **`perceptual`**: the 64-bit pHash is packed big-endian into the first 8 bytes of the 32-byte field, algorithm `PHash`. It is omitted when the hash is all zeros (the program rejects a zero hash).
- **`creator_wallet`** is left unset: the program requires the creator to co-sign, and a wallet can't be both provider and creator.
- **`generated_at`** is left unset — the app knows when it anchored (the `slot`), not when the media was generated.
- The AI **model** is not part of the on-chain record; the record's *provider* is what identifies the tool.

## Quick start

Prerequisites: [Node.js](https://nodejs.org/) ≥ 18 and [pnpm](https://pnpm.io/installation) ≥ 9.

```bash
pnpm install
cp app/.env.example app/.env.local   # optional: RPC endpoint / cluster
pnpm dev:app                         # http://localhost:3000
pnpm build                           # production build
```

The app targets **Solana devnet** by default. The public devnet RPC (`api.devnet.solana.com`) is rate-limited and sometimes unavailable; set `NEXT_PUBLIC_SOLANA_RPC_URL` to a dedicated endpoint for anything beyond light use. See `app/.env.example`.

## Getting a wallet anchoring on devnet

Anchoring is limited to registry-approved providers, so a fresh wallet can connect and verify but not anchor. Three things have to happen once, in this order:

1. **Initialize the registry.** `init_registry` can only be signed by the program's *upgrade authority* (the wallet that deployed it). As of writing the devnet registry has not been initialized, so this comes first, from the deployer wallet — see `anchor/README.md`.
2. **Approve your provider wallet.** The registry authority calls `approve_provider(provider, name, c2pa_cert_identity)` for your wallet's address. The app shows you the exact address to send (wallet menu → "Not an approved provider yet").
3. **Claim it in the app.** Connect the wallet, press **Claim provider registration** (one small signed transaction), and the Anchor page unlocks.

The wallet also needs devnet SOL: about 0.0022 SOL of rent per anchor plus a fee (and a little more for the one-time claim).

## Updating the generated client

`app/lib/generated/origina` is generated from `app/idl/origina.json`. When the program's IDL changes, regenerate it:

```bash
pnpm --filter @origina/app generate:client
```

## Testing on-chain behavior locally

`app/scripts/chain-integration.ts` exercises the app's chain layer against a local validator running the program's **real deployed bytecode** — registry setup, provider lifecycle (none → pending → active → revoked), anchoring, duplicate handling, exact and near lookups, and the failure modes.

```bash
solana program dump 8n7frgF7141JQnvUVtqxXid6RoZbfv7J7mrxQ9hnTFbi origina.so --url devnet
solana-keygen new --no-bip39-passphrase --outfile deployer.json
COPYFILE_DISABLE=1 solana-test-validator --reset \
  --upgradeable-program 8n7frgF7141JQnvUVtqxXid6RoZbfv7J7mrxQ9hnTFbi origina.so "$(solana-keygen pubkey deployer.json)"

DEPLOYER_KEYPAIR=deployer.json pnpm --filter @origina/app test:chain
```

For manual UI testing against that validator, run `pnpm --filter @origina/app setup:local` (with `DEPLOYER_KEYPAIR` and `PROVIDER_ADDRESSES="<address>:<name>"`), then start the app with `NEXT_PUBLIC_SOLANA_CLUSTER=localnet`.

## Known limitations

- **Lookup scales linearly.** Finding a record by file hash scans the program's accounts with an RPC filter, and near-match search compares every record's perceptual hash client-side. Fine for an MVP; it will need an indexer as the record count grows.
- **Perceptual hash is byte-level.** `computePHash` samples raw file bytes, not decoded pixels, so a crop or re-save often won't register as a near match. A production version should hash decoded pixels.
- **No C2PA parsing yet** (see the sentinel above), and no creator co-signing flow.
- The seeded posts in the Social feed are sample content; their badges are labelled as samples and are not on-chain records.
